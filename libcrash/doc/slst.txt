q: What is the significance of the ordering of polygon ids in the scenery list?

a: There may be multiple reasons for the ordering. The first reason is at
   least partly for the draw order. The second may be for optimal encoding
   of the corresponding delta lists.
   
   Polygon ids are processed in their order in the scenery list. For each
   polygon id, the coordinates for the corresponding polygon are loaded 
   and perspective transformed, and then a polygon primitive is created 
   and placed into a display list bucket (i.e. bucket sorted). The index 
   of the bucket which the polygon is placed into is dependent on the 
   minimum average z value of perspective transformed primitives detected
   thus far. More precisely this average value is scaled and offset relative
   to a given z location, likely that of some near plane, so that the range
   of polygons placed in the display list are exactly those within the 
   viewing frustum, and any outside valid indices are discarded.
   
   For whatever the order of polygon ids in the scenery list, ids for 
   polygons with average z values that are larger than that of some 
   preceding polygon are all placed into the same bucket:
   
   100     [100]: 100
   90      [90]: 90
   80      [80]: 80, 90, 100, 90, 80
   90      [70]: 70
   100  => [60]: 60
   90
   80
   70
   60
   
   If polygon ids were not placed into the bucket with index [dependent
   on] the current minimum average z value, but rather directly into the
   bucket with index [dependent on] the current *polygon* average z value,
   then the order of polygons in the scenery list would have no effect on
   the draw order:
   
   100     [100]: 100, 100
   90      [90]: 90, 90, 90
   80      [80]: 80, 80
   90      [70]: 70 
   100  => [60]: 60
   90
   80
   70
   60
   
   (any ordering of the average z values on the left and thus the 
    corresponding polygon ids would yield the same display list order;
    any permutation of a list always sorts to the same list)
   
   The minimum average z logic thus gives some significance to the 
   ordering of polygon ids in the scenery list. In particular, the 
   order of polygon ids in the display list is exactly the order of 
   polygon ids in the scenery list. But with the catch that average z
   values of polygons in a particular bucket are not necessarily all the
   same and thus are not all some constant scaling and addition of the 
   index.
   
   This means that object polygons (with varying z position at a 
   particular path point) can weave into the display lists between the
   constant positioned scenery polygons while the higher accuracy non
   z-based sort order for the scenery polygons is maintained.

extension: 'working' (modifiable/expandable/contractable) object interface

- the object is no longer read-only and therefore we can
  - allocate new objects of the type
  - initialize objects of the type
  - add to or remove from, objects of the type
  - save/write objects of the type
- when an object is initially read, it will be in packed form to fit 
  minimal space in the file-that is, all referenced memory for the 
  object is stored contiguously in the structure, and all objects of
  that type are stored contiguously. thus in order to add to or remove 
  from the object without extending into other parts or other objects
  it must first be unpacked.
- after an object is unpacked it must be (re)packed into a contiguous
  region before it can be saved/written
- the following operations are therefore required for this interface:

  - object_read()
  - object_write()
  - object_unpack()
  - object_pack()
  - object_alloc()
  - object_init()
  - object_new() [opt.]
  - object_extend() [opt., unpacked only]

- a new object of the type should be unpacked by default. packed objects
  are allocated additional (possibly variable length) memory, that is-in 
  addition to the variable length memory for some flexible array member. 
  unpacked objects should only be allocated memory for the structure and 
  sufficient number of flexible array members. references within the 
  unpacked object to external objects otherwise become references to
  internal objects once the object is packed.
  
- only memory for sufficient number of flexible array members is 
  required for a newly allocated unpacked object; once the object is 
  packed it does not matter how much extra was allocated, for the 
  unpacked object will be freed/reallocated 
  
- the c++ alternative approach with vectors would essentially be doing 
  the same thing by allocating some pre-set amount of extra memory 
  in advance to account for appends/extension (without having to realloc
  for each new item). the difference here is that the unpacked object
  can be memcpy'ed directly to get the initial part of the packed object
  and in most cases simply reallocated
